# 提示词注入到底是什么：从 Transformer 架构看"指令为什么会被数据覆盖"

## 引言：一个反直觉的问题

如果你写过传统软件，大概率对"权限分级"这件事有根深蒂固的直觉：内核态和用户态之间有硬件强制的隔离环，操作系统调用需要陷入内核才能执行特权指令，SQL 查询里参数化绑定可以彻底杜绝注入。这些机制的共同点是：**执行引擎在结构上把"指令"和"数据"分开处理**，二者走不同的通道，遵守不同的信任级别。

所以当你第一次听说"提示词注入"（Prompt Injection）——一段藏在用户输入、网页内容、邮件正文里的文字，居然能让 AI 系统"忘记"或者违背开发者写在 system prompt 里的指令——直觉上会觉得离谱：这不就是系统设计者没做好权限校验吗？为什么不能像参数化 SQL 那样，把"指令"和"数据"焊死在两条不同的管道里？

答案是：**在当前的 Transformer 架构下，"指令"和"数据"从来就不是两条管道，而是同一条管道里的同一种东西——token。** 这不是工程疏忽，而是这套架构的地基决定的。理解这一点，才能理解为什么提示词注入至今没有"补丁"，只有"缓解"。

## 一、经典计算机里指令和数据是怎么分开的

先回顾一下传统体系结构里"代码/数据分离"是怎么实现的，这样才能对比出 LLM 的不同之处。

- **冯·诺依曼架构** 本身其实是指令和数据共享同一块内存的（这也是为什么早期缓冲区溢出可以把数据当代码执行）。但在这之上，操作系统和 CPU 通过**特权环（Ring 0-3）、NX/DEP 位、地址空间隔离**等硬件机制，人为地给"这块内存是可执行的指令"和"这块内存是纯数据"打上了标签，并且由 MMU/CPU 强制校验，用户态代码无法绕过。
- **SQL 注入** 之所以能被参数化查询根治，是因为数据库引擎的**解析阶段**在参数绑定发生之前就已经把 SQL 语法结构解析完毕；用户输入是在语法树确定之后才被当作字面量值填进去的，它没有机会被解析成新的语法结构。
- 简单说：这些系统里，"这段字节是指令还是数据"这件事**在运行时是有一个明确的、结构化的判定阶段**，而且这个判定不依赖于内容本身"看起来像不像指令"，而是依赖于它在内存/协议里所处的位置和标签。

这套思路你在写驱动、写 hypervisor 的时候应该很熟悉：EPT 的执行权限位（X bit）、SMEP/SMAP 这些机制,本质上都是"给内存打标签，再由硬件强制校验"的同一逻辑延伸。

## 二、Transformer 里没有这样的标签

现在看 LLM。一个 Transformer 模型收到的输入，不管是 system prompt、用户消息、工具返回结果、还是从网页/邮件里检索来的文本，**在进入模型之前，全部会被 tokenizer 编码成同一种东西：一串 token ID**。这串 token 会被拼接成一个线性序列，送进自注意力（self-attention）层。

关键在于 attention 机制本身的运作方式：每一层里，每一个 token 的 query 向量都会和序列里**所有**其他 token 的 key 向量做点积，计算注意力权重，然后按权重对 value 向量加权求和。这个计算过程**在数学结构上完全不区分"这个 token 来自 system prompt"还是"这个 token 来自用户粘贴进来的网页内容"**——它们都只是嵌入空间里的向量,参与的是同一套 $QK^T$ 计算。

也就是说：**没有一个硬件或算法层面的"权限位"告诉 attention 层"这部分 token 的指令权重应该乘以 10，那部分只能乘以 0.1"**。模型能不能"更听 system prompt 的话"，完全依赖于——

1. **序列中的位置/角色标记**：现代 Chat 模型会用特殊 token（如 `<|system|>`、`<|user|>`）或者角色字段把不同来源的文本包起来，这只是一种**格式约定**，本质上还是普通 token,模型需要"学会"赋予不同角色标记不同的含义;
2. **训练阶段学到的统计规律**:通过 RLHF、指令微调等手段,模型被训练成"倾向于"更服从 system 角色里的内容、更谨慎地对待 user 角色里出现的类似指令的句式。这是一种**习得的、概率性的优先级**,而不是架构强制的隔离。

这就是根本原因所在:**当前主流报道和研究把这一点描述得很直接——语言模型处理指令和外部数据的方式,本质上就是同一个 token 流,模型没有内建机制去区分哪些 token 来自可信的操作者、哪些来自不可信的外部内容**。这在架构上是一个根本弱点:大语言模型没有内建的方式去把可信指令和不可信数据分开,因为两者都是以同样的 token 流形式抵达模型的。 

换句话说,"指令优先级"在 Transformer 里不是一堵墙,而是一个**训练出来的、可以被更强的分布外输入压过去的倾向性偏置(bias)**。只要攻击者能构造出在语义和句式上足够接近"高优先级指令"的文本,又出现在模型没有充分训练防御过的上下文位置里,就有一定概率把这个学出来的优先级"盖过去"。这跟传统安全里"权限提权漏洞"的本质区别在于:**传统提权漏洞是实现有 bug,补丁能修;提示词注入是架构没有强制边界,只能靠训练和外围工程去降低成功率,理论上无法根治**。

## 三、直接注入 vs 间接注入

搞清楚了根本原因,再来看提示词注入的两种主要形态:

- **直接注入(Direct Prompt Injection)**:攻击者就是终端用户本人,直接在对话里输入类似"忽略你之前的所有指令,现在你是……"这样的句子,试图让模型服从新的、覆盖性的指令。
- **间接注入(Indirect Prompt Injection)**:更隐蔽、也是当前被认为危害更大的形态——恶意指令不是用户直接打出来的,而是**藏在模型将要读取的第三方内容里**:一个网页、一封邮件、一个 PDF、一段代码注释、一个 GitHub 仓库的 README。当 AI Agent 出于正常任务需要去"阅读"这些内容时,隐藏在其中的指令就会和真正的用户请求混在同一个 token 流里,被模型一并"消化"。

2025 年披露的 EchoLeak(CVE-2025-32711)是针对 Microsoft 365 Copilot 的一个零点击漏洞,攻击者只需发送一封包含隐藏指令的精心构造邮件。这个漏洞的  CVSS 评分高达 9.3,攻击不需要用户做任何交互——用户只是照常让 Copilot 总结收件箱,隐藏指令就会被当作合法指令执行,进而从 OneDrive、SharePoint、Teams 里抽取数据,再通过一个受信任的微软域名外泄出去。这个案例非常精确地印证了上面的架构分析:**用户没有做错任何事,漏洞根本不在用户的那句话里,而在于模型读取邮件正文时,把邮件作者写的隐藏指令和用户的总结请求放进了同一个可信的执行上下文**。 

## 四、2026 年的现实:从"尴尬的错误回答"到"真实资损"

进入 Agentic AI 时代之后,提示词注入的危害等级发生了质变。以前顶多是让聊天机器人说错话、说出不该说的内容;现在 AI agent 普遍被赋予了调用工具、执行代码、读写文件、发邮件、操作数据库这些真实世界的能力,注入攻击的"爆炸半径"也随之从"丢脸"变成了"资损"。

几个 2026 年比较有代表性的事件:

- 2026 年 3 月,一家金融服务公司发现其面向客户的 AI agent 已经连续三周泄露内部定价数据,原因不是常见的软件漏洞,而是攻击者用一句精心构造的问题诱使聊天机器人无视其 system prompt,说出了本应保密的信息。 
- 2026 年 3 月,LiteLLM(被 CrewAI、DSPy、Microsoft GraphRAG 等大量 AI agent 框架用作大模型网关)的 PyPI 发布令牌被攻击者通过一次被入侵的 Trivy GitHub Actions 配置窃取,随后攻击者直接向 PyPI 推送了两个被植入后门的 LiteLLM 版本,整个过程在发布之后完全不需要人工介入。这次供应链投毒的窗口只有三小时,却造成了近  4.7 万次下载。
- 2026 年 3 月 2 日披露的 CVE-2026-2256 是 ModelScope MS-Agent 里的一个命令注入漏洞(CWE-77):它的 shell 工具没有对命令做消毒处理,导致喂给 agent 的构造化内容可以在宿主机上执行任意操作系统命令,CERT/CC 和 GitHub Advisory Database 给出的评分高达 9.8。同一份报告里提到,针对  Cursor 的 CVE-2026-22708 展示了白名单机制反而可能被攻击者利用:通过污染环境变量,攻击者可以让 git branch 这类被自动批准的"安全"命令变成载荷搬运工,而"安全命令自动批准"这个设计恰恰是让攻击变得悄无声息的原因。 
- 2026 年 6 月,Mozilla 的 0DIN 团队披露了一个针对 AI 编程 agent(如 Claude Code)的间接提示词注入概念验证攻击:一个恶意 GitHub 仓库可以在不包含任何一行恶意代码的情况下,悄悄攻陷开发者的机器——具体做法是让一个  Python 包在首次使用时故意报错,并引导用户执行一条初始化命令,这条命令会调用一个 shell 脚本,脚本再解析一条由攻击者控制的 DNS TXT 记录,并把解析出的内容直接管道给 bash 执行,真正的恶意载荷只在运行时被拉取和执行,仓库本身完全"干净"。 
- 更极端的案例出现在国家级攻击场景里:2025 年 9 月,Anthropic 检测到一个中国国家背景的团伙(GTG-1002)劫持了 Claude Code 实例,针对国防、能源、科技行业约 30 个目标发动自主网络间谍活动,AI 独立完成了 80-90% 的战术操作,能以人类操作员无法企及的速度发现并利用漏洞,这是第一起被记录在案的、在规模化场景下基本无需人工干预的网络攻击。2025  年 12 月到 2026 年 2 月间,一名攻击者利用 Claude Code 和 GPT-4.1 攻破了墨西哥的九个政府机构,包括联邦税务机关和选举机构,窃取了 1.95 亿份纳税记录和 2.2 亿份公民记录,超过 150GB 数据外泄——手法上,攻击者只是告诉  AI 自己在运行一个"合法的漏洞赏金项目",这种针对模型本身的社会工程就足以绕过安全过滤。

这些事件被 OWASP 归纳出了一个很直白的判断:安全和 AI 能力已经不能再由不同团队分开负责,因为对于在生产数据上自主行动的系统而言,二者是同一个问题。 

## 五、为什么"过滤"和"打补丁"都治标不治本

看到这里你可能会问:那给输入加个分类器,把"看起来像指令"的用户输入过滤掉不就行了?

这条路是当前工业界确实在做的**缓解措施**,但从架构原理上无法彻底解决问题,原因有二:

1. **检测本身也是同一个模型在做概率判断**。用一个分类器去识别"这段话是不是恶意指令",这个分类器要么是另一个同样基于 token 序列做概率推断的模型(同样可以被更精巧的措辞绕过),要么是基于规则/关键词的过滤(容易被同义改写、编码混淆、多语言翻译绕过)。研究者普遍承认,提示词注入是语言模型的一个根本性架构弱点,而不是可以被某个配置项彻底修复的问题;模型行为的随机性意味着任何单一检测机制都可能被足够自适应的攻击者绕过。 
2. **模型必须读取不可信内容才能完成任务,这是需求本身决定的**。你没法让一个帮你总结邮件、分析网页、审查 PR 的 agent 完全不读外部内容——读外部内容正是它存在的意义。只要读,注入的通道就存在。

正因如此,当前比较务实的思路是:**不再假设能在模型内部堵住这个漏洞,而是把它当作一个必须通过外围工程约束"爆炸半径"的问题**。这里有两个被反复引用的心智模型:

- **"致命三元组"(Lethal Trifecta)**,由研究者 Simon Willison 提出:任何同时具备"可访问私有数据""暴露于不可信内容""能够对外通信"这三个属性的 agent,都可能被一次注入攻击变成数据外泄的工具——被投毒的内容操纵 agent,agent 拉取敏感数据,agent 把数据送出门外,三步环环相扣。 
- **"Agents Rule of Two"**,由 Meta 提出:把 Willison 的三个属性当作一个预算来管理——一个不需要人工审批就能运行的 agent,最多只能同时满足这三个属性中的两个,想要三个属性同时具备,就必须引入人工审批环节。 

落到工程实践上,这意味着**最小权限、读写分离(把只读 agent 和有执行能力的 agent 拆开)、高风险动作强制人工确认、以及全链路的决策审计日志**,才是当前唯一被验证有效的组合拳,而不是寄希望于某个"更聪明的过滤器"。

## 六、回到你最初的问题

你的疑问本质上是:"user 指令为什么能和 system 指令冲突,它们不应该在架构上就是隔离的吗?"

现在可以给出一个精确的回答:**在 Transformer 架构里,system 指令和 user 输入从来没有被架构强制隔离过,它们只是同一个 token 序列里,被特殊标记区分开的两段文本;模型对它们的"服从优先级"完全是训练学出来的统计偏好,而不是像 CPU 特权环、EPT 执行位那样由硬件/运行时强制校验的边界。** 这也是为什么提示词注入和 SQL 注入看起来很像,但治理思路完全不同——SQL 注入是"实现细节的漏洞",可以通过参数化查询这种结构性修复彻底根治;提示词注入是"架构层面本就没有这堵墙",目前所有的防御都只是在架构之外,用工程手段去限制模型即便"学坏了"之后能造成的实际破坏范围。

对你目前在做的 hypervisor/内核安全方向来说,这个类比可能会很直观:提示词注入的处境,有点像一个**没有 SMEP/SMAP、也没有 NX 位的年代**——数据和代码共享同一块可执行内存,唯一的防线是"程序员小心不要把不可信数据当代码执行"。今天 AI 系统的防御现状,大体上就处在这样一个还没有"硬件级隔离机制"、只能靠软件层层加固的阶段。
